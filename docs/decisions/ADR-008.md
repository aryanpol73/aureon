# ADR-008: Multi-Tenancy and Data Isolation

**Status:** Accepted, amended

## Context

Aureon must guarantee absolute tenant data isolation across all queries. Accidental data leaks between workspaces would be catastrophic for user privacy.

## Decision

Implement PostgreSQL Row-Level Security (RLS) as a fail-closed foundational defense, combined with mandatory application-level scoping.

- RLS Policy: Every multi-tenant table enforces ENABLE ROW LEVEL SECURITY and FORCE ROW LEVEL SECURITY. Policies evaluate workspace_id = current_setting('app.workspace_id', true).
- Amendment from Spike S2 / F5: Application queries must also explicitly include WHERE workspace_id = $1. This eliminates query planner misestimates caused by opaque current_setting() evaluations, ensuring fast Index Scans without memory-intensive Sort nodes.
- Connection Pool: withTenant(workspaceId, tx) sets local session variables safely and cleans them up before releasing connections back to the pool.
- Composite Foreign Keys: Foreign keys must include (workspace_id, entity_id) to prevent cross-workspace references at the database schema level.

## Alternatives

- **Database-per-tenant:** High operational overhead, slow schema migrations across hundreds of databases, and resource exhaustion.
- **Schema-per-tenant:** Limited PostgreSQL schema limits, complex migration tooling, and difficult connection pooling.
- **Application-only WHERE filtering:** Catastrophic single point of failure; a single missing WHERE clause exposes foreign tenant data.

## Consequences

- **Positive:** Multi-layered defense-in-depth: database rejects cross-tenant reads/writes even if application code is buggy; query planner receives explicit filter parameters.
- **Negative:** Schema definitions require composite foreign keys; developer discipline required to use withTenant consistently.
