# ADR-012: Agent Execution Architecture and State Machine

**Status:** Accepted

## Context

Autonomous multi-step agents can easily get stuck in infinite execution loops, hallucinatory tool invocations, or non-deterministic states if not strictly governed.

## Decision

Structure AI agents as deterministic, observable finite state machines:

- State Machine Steps: Plan -> Execute Step -> Inspect Observation -> Reflect -> Complete or Transition.
- Hard Execution Bounds: Fixed maximum step count, maximum token budget, and wall-clock timeout per run.
- Tool Boundary Enforcement: Agents execute tools through an explicit registry. Tool schemas strictly forbid workspace_id or user_id inputs (these are injected by the execution runtime).
- Persisted Runs: Every agent run, step, tool call, and tool output is persisted to PostgreSQL for auditability and replay.

## Alternatives

- **Unconstrained LangChain / AutoGPT style loops:** Prone to infinite execution cycles, difficult to test, and non-deterministic error recovery.
- **Hardcoded procedural workflows:** Lacks the adaptive reasoning capabilities required for open-ended user goals.

## Consequences

- **Positive:** Predictable agent behavior, easy debugging via saved execution traces, and foolproof tenant boundaries on tool calls.
- **Negative:** Requires upfront engineering of state machine transitions and execution harnesses.
