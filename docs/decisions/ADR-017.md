# ADR-017: Error Handling and Fault Tolerance

**Status:** Accepted

## Context

Aureon must avoid unhandled exceptions, cryptic 500 internal server errors, and untyped error bubbling across module boundaries.

## Decision

Enforce a structured error-handling paradigm:

- Domain and Application Layers: Use a functional Result<T, E> type for expected business errors (e.g. NotFound, ValidationError, BudgetExceeded). Domain code does not throw exceptions for anticipated error states.
- API Boundary: Uncaught exceptions are intercepted by a global Fastify error handler and serialized to RFC 7807 Problem Details (status, type, title, detail, instance). Internal stack traces are never exposed to clients.
- Background Workers: Transient errors trigger exponential backoff retries; permanent errors route jobs to dead-letter queues with complete error provenance.

## Alternatives

- **Traditional try/catch exception bubbling everywhere:** Leads to unhandled rejections, missing error types, and unexpected service crashes.
- **Ad-hoc JSON error responses ({ error: string }):** Inconsistent client experience and poor API interoperability.

## Consequences

- **Positive:** Exhaustive compile-time error checking, standardized machine-readable HTTP errors, and reliable background failure recovery.
- **Negative:** Requires wrapping return values in Result constructs throughout application services.
