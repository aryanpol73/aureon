# ADR-005: Background Job Queue (pg-boss with Transactional Enqueue and Explicit Configuration)

**Status:** Accepted with conditions

## Context

Asynchronous tasks (document extraction, chunking, embedding, daily planning, notifications) require at-least-once delivery, retry mechanisms, dead-letter archiving, crash recovery, and transactional enqueue semantics.

## Decision

Adopt pg-boss on PostgreSQL 17. Jobs enqueued within an active database transaction commit or rollback atomically with domain state.

Conditions accepted from Spike S1/S1b evidence:

1. Crash-recovery target is <= 2 minutes; default worker heartbeat is 30s.
2. Every queue explicitly declares its pollingIntervalSeconds, batchSize, and localConcurrency in validated configuration. Library defaults are never used implicitly. Bulk queues use batchSize >= 10, concurrency >= 4 to engage burst mode (>20 jobs/s).
3. Queue creation remains in the deployment release step. Workers execute a fail-fast startup check verifying queue existence.
4. Release step issues explicit GRANT USAGE ON SCHEMA pgboss to the runtime role.

## Alternatives

- **BullMQ + Redis:** Requires two-phase commits to sync Postgres writes with Redis job enqueue. Network splits can cause ghost jobs or missed jobs.
- **RabbitMQ / Kafka:** Unnecessary infrastructure overhead for the current scale, lacking transactional cohesion with PostgreSQL.

## Consequences

- **Positive:** Enqueueing a job inside a transaction is 100% atomic with domain data updates. Zero orphaned jobs on rollback.
- **Negative:** Queue operations generate PostgreSQL WAL and table I/O; table autovacuum and archive partitions must be monitored.
