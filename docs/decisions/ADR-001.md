# ADR-001: Architecture Style (Modular Monolith with Asynchronous Workers)

**Status:** Accepted

## Context

Aureon requires strong domain boundaries across identity, projects, knowledge, AI, and memory. It must support low-latency interactive workflows, high-throughput asynchronous document ingestion, and multi-tenant isolation, while avoiding premature distributed-systems overhead at the start of the product lifecycle.

## Decision

Adopt a Modular Monolith architecture with asynchronous background workers. Domain modules communicate via explicit application service interfaces, sharing a single PostgreSQL database with isolated schema boundaries. Background workloads (document extraction, chunking, embedding, planning) run in detached worker processes consuming from a PostgreSQL-backed job queue.

## Alternatives

- **Microservices:** Rejected due to operational complexity, distributed transaction overhead, network latency, and premature network boundary enforcement.
- **Traditional Monolith without Modular Boundaries:** Rejected due to high risk of circular dependencies, schema entanglement, and inability to independently scale or refactor domains.

## Consequences

- **Positive:** Single deployment target for the web API, straightforward local development, simplified transactional guarantees, unified tracing, and zero network hops for internal domain calls.
- **Negative:** Requires rigorous automated tooling (dependency-cruiser, strict ESLint boundaries) to prevent cross-module coupling and direct database access across domains.
