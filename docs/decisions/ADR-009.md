# ADR-009: Caching Strategy and Redis Layer

**Status:** Accepted

## Context

Interactive AI workflows require fast retrieval of ephemeral state, rate-limiting tokens, session validation caches, and AI kill-switch status without adding unnecessary database read contention.

## Decision

Adopt Redis as a dedicated caching and ephemeral state store. Redis is treated as an ephemeral cache: all persistent data resides in PostgreSQL. Every cache key uses structured namespacing (aureon:<tenant_id>:<module>:<key>) with explicit TTLs. The application must gracefully degrade to PostgreSQL if Redis is unavailable.

## Alternatives

- **In-memory local node cache:** Does not share state across multiple API or worker instances, complicating rate-limiting and invalidation.
- **PostgreSQL unlogged tables:** Adds connection and lock contention to the primary relational cluster.

## Consequences

- **Positive:** Sub-millisecond read latency, atomic token-bucket operations, and decoupled read load from PostgreSQL.
- **Negative:** Requires cache invalidation strategies and health-check fallbacks.
